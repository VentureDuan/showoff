## 详情 01：Ask-Venture Plugin

### 首屏文案

让跨模块排障，从找人问背景走向沿证据调查。

面向研发、测试和运营，将真实故障中提炼的领域知识、调查方法与 MCP 工具组织为内部排障插件。独立完成用户调研、需求定义、设计开发、推广与迭代。

### 主要图解：调查中的证据链

用户提供环境、目标与现象 → Gateway 确认范围 → 按需加载领域 Skills → 查询日志、任务、数据库和实例并对照代码 → 形成结论、证据、未确认项与下一步。

强调调查可随证据下钻和调整，不表现为只能按固定工具顺序执行的脚本。

### 章节顺序

1. 原来的成本：数据分散，跨模块时需寻找同事、重新介绍上下文。
2. 实际案例：截图提示 task not found → 回溯原任务 → 复制前空间检查失败 → 确认目标 L2 容量不足。区分原始失败与后续取消报错。
3. Skills 如何设计：按生命周期组织、按需加载、现场版本对齐、按标识关联证据、区分原始与次生故障、证据不足时停在已知边界。
4. Evaluation 如何运行：历史案例回放、自动规则检查、人工复核，离线与隔离环境两层验证，加 Skills 前后对照；越权为硬失败。
5. 更多调查：磁盘签名冲突、本地与云端状态分裂，各用短案例链接主旨。
6. 边界与迭代：已实际运行 Evaluation；LLM as judge 尚未实施。根因调查、研发修复与线上恢复分别说明，不伪造收益比例。

## 详情 02：云游戏启动性能分析 Agent

### 首屏文案

让告警后的第一轮调查提前完成。

支持定时、主动和告警触发，由程序准备结构化事实，LLM 结合领域规则解释业务异常，为支持人员止损、研发继续定位根因提供上下文。负责全部模块设计与实现。

### 主要图解：指标到业务解释

实例基础状态正常 + 预启动失败 + 异常集中于灰度实例；结合“该业务必须预启动成功才能分配”的规则，解释为何实例充足但用户排队。

图分清事实、业务规则、分析结论与人员行动；不把灰度相关性直接画成已证明的代码根因。

### 章节顺序

1. 告警场景：实例充足、分配排队的矛盾。
2. 三种触发入口汇入共同分析过程；不新增触发频率。
3. 程序、Skill、LLM 与人员分工：确定性查询计算 → 领域规则 → 解释与报告 → 人员决策。
4. 报告内容示意：阻塞条件、影响范围、灰度关联、证据、待查问题与处置建议。明确是脱敏结构示意，不冒充真实报告截图。
5. 协作链：支持人员通知运维止损，研发承接报告，通过 Ask-Venture 深入预启动失败原因。用人员节点明确两个项目间的交接。
6. 持续优化：定时分析阶段耗时，为产品计划与业务流程迭代提供依据。

原故障回滚恢复与当前工具支持的典型流程分开，不拼接成未经确认的全程自动实战。报告投递方式若展开，沿用 Webhook 与下游通知的已知信息。

## 详情 03：内容分发与分层加速

### 首屏文案

先让实例可用，再让游戏跑得更快。

面对 200 GB 以上游戏包、1–2 Gbps 实例带宽及约 1.5 万路订单，围绕两小时版更开服窗口优化内容交付。深度参与全流程，重点负责部署与加速。

### 主要图解：交付关键路径与存储层级

装载 → 分发 → 部署 → 实例可用；加速作为后置工作独立表达。旁边用 L3 Ceph 网络盘、L2 SSD、L1 内存盘解释分层，不画成必须逐级串行迁移。

### 章节顺序

1. 约束：包体、网卡、并发、总窗口、95% 业务成功率与冗余机器。
2. 四阶段领域模型与部署/加速解耦。
3. 优化组合：高性能装载与 rclone、Dragonfly P2P、CDC、打包分片流水线。
4. 单次差量样本：200 GB 原包、170 GB 文件级差量、15 GB CDC 差量；标记同一代表性对比，不暗示全部版本固定收益。
5. 设计取舍：内容包全局唯一 ID；打包但不压缩，用端到端收益做判断。
6. 多轮典型水平：约 70 分钟超过 98% 部署可用；约 140 分钟 90% 加速完成；约 160 分钟 99% 加速完成。采用里程碑，不插值伪造连续实测曲线。
7. 观测推动改进：双开第二路复用同实例第一路内容，加速收尾由约 210 分钟降至约 160 分钟；不标注未经确认的旧百分位。

数据说明紧邻指标：数据为脱敏取整、基于多轮压测的回忆。阶段 P98 的多轮均值放在深入阅读处，不抢占首屏，不相加推导总耗时。

## 详情 04：实例任务编排与调度协同

### 首屏文案

让后台任务，等到正确的时机再执行。

在 SaaS 与 IaaS 之间协调用户占用、实例调度和后台资源操作。主导系统设计与实现，部分 worker 执行逻辑及 IaaS 接口封装由同事完成。

### 主要图解：角色与阶段协作

运营提交任务 → CGInstance 校验并抢锁 → 同步请求下调度 → 确认禁止新分配、等待已有用户退出 → 扫描并执行任务 → 确认结束及可用 → 按任务类型收尾。

以任务阶段示意、角色泳道表达，不冒充精确内部状态枚举；维护类任务可恢复调度，退订类任务不画回可服务池。

### 章节顺序

1. 退订场景：资源要回收，但用户仍在使用。
2. 两条约束：占用中不执行任务，执行中不外放。
3. 主流程与职责：调度维护占用，CGInstance 管理锁和实例状态，定时扫描推动执行。
4. 失败分支：activity 按配置重试，或保持锁定等待处理。
5. 重启恢复：无状态 worker、数据库保存执行数据；不补写恰好一次、幂等与自动解锁保证。
6. 完成后的可用确认、巡检与锁释放；锁由 CGInstance 负责。

## 详情 05：实例 Agent 管理与状态收敛

### 首屏文案

实例会重置，服务版本和业务状态仍要重新对齐。

负责实例侧架构设计与代码实现，以 CGInstanceAgent 管理服务生命周期并汇聚状态，适应无盘裸金属环境，面向约 20 万实例设计状态上报。

### 主要图解：两幅职责不同的图

1. 更新图：云端目标版本 → 先自更新 CGInstanceAgent → bootload 对比版本 → Bundle 更新其他 Agent。
2. 上报图：CGVmAgent / lightstreamer / CGMetricsAgent → CGInstanceAgent → Union；心跳与业务状态使用不同标签，业务状态变化触发 + 失败持续重试 + 每 10 分钟兜底。

### 章节顺序

1. 四 Agent 的职责，强调 CGInstanceAgent 是镜像内置管理入口。
2. 基础设施变化：KVM 迁移到无盘裸金属，重启还原已部署服务。
3. 两级更新的分工与顺序；收到对应 Agent 状态上报才判定部署成功。
4. 状态方案取舍：云端查表比较、考虑集中缓存、最终下放比较逻辑。
5. 收敛机制：变化上报、失败无限重试、10 分钟兜底；感知心跳发送失败也触发业务上报。
6. 心跳超时：云端五周期未收到则标记“已关机”，说明这是判定状态，不是物理断电证明。

20 万是设计承载规模，不附未验证吞吐数字，也不宣称 Redis 普遍无法支持该规模。

## 建议设计系统与静态首版范围

模式：Redesign · Preserve。保留网站暖色工程手记风格及现有明暗主题，重组项目区域。

- 五尺度：构图变化 5/10、动效强度 5/10、信息密度 5/10、素材依赖 2/10、品牌保留 9/10。
- 配色：沿用 CSS 变量，暖白 #f7f7f2、白卡 #fff、正文 #252520、次级 #71716a、线条 #e7e7df、琥珀 #ffb629、强调正文 #b84a08；深色使用现有主题对应变量。
- 字体：沿用 Microsoft YaHei UI / PingFang SC；技术标识 Consolas。正文 16–18px，主标题 32–48px。
- 间距：8px 基础，16/24/32/48/64px 层级；主卡片 24px 圆角、内部图节点 12px；沿用轻阴影，不增加高强度发光。
- 图形：统一线条图标、标注清楚的节点和连线；每个项目不同图形构图。不使用假产品截图。
- 后续动效：短状态反馈约 200–300ms；关键过程可分步播放、暂停与重播；减少动态效果偏好下完整静态阅读。
- 手机：横向图改为纵向步骤或分组，不缩小到无法阅读；解释不只依赖 hover。

确认此结构与设计系统后，制作可查看的静态 v0：项目列表、Ask-Venture 和内容分发的代表性详情布局，其余详情先展示核心结构。优先确认风格和图文比例，再完善全部内容与动画。
