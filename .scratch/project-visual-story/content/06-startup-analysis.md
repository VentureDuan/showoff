# 云游戏启动性能分析 Agent

## 核心定位（用户提供）

让告警发生后的第一轮调查提前完成，支持人员先采取止损措施，研发再沿证据继续定位根因。

项目既做阶段耗时分析，也结合业务规则解释启动、分配异常。候选展示名为“云游戏启动与分配分析 Agent”，仅作为编辑建议，尚未替换原项目名称或 URL。

## 个人贡献、触发与受众

- 个人贡献：负责全部模块设计与实现。
- 最终确认三种触发：定时、用户主动发起、异常告警。替代早期仅记录定时触发的不完整描述。
- 本轮最新口述中的报告受众：研发、运维、测试、售前。
- 先前还确认运营、产品、技术支持使用报告：研发与产品据此制定计划、迭代流程，测试与技术支持判断灰度影响。这里保存两次口述，网站可概括为“研发及业务支持团队”，正文按场景说明具体角色，不强行将不同角色当成同一部门。

## 业务价值

1. 持续优化：发现当前流程的卡点与长耗时步骤，为研发、产品制定迭代计划提供依据。
2. 灰度观察与止损：关联影响范围、业务阻塞条件与灰度特征，帮助支持人员判断异常并通知运维停止灰度、回滚。
3. 研发交接：将已收集事实、业务解释和待查问题交给研发，结合 Coding Agent 与 Ask-Venture 继续根因调查。

## 技术分工：程序先准备事实，LLM 结合业务知识解释

| 层次 | 职责 |
| --- | --- |
| 程序 | 预先查询数据，完成确定性计算，准备结构化事实 |
| 领域 Skill | 提供业务规则、状态含义与分析方法 |
| LLM | 选择相关 Skill，关联事实与规则，组织解释和报告 |
| 人员 | 决定并执行止损，继续根因排查与修复 |

### 告警触发的典型流程

1. 接收告警与监控信息。
2. 程序预先查询监控指标、实例状态、预启动结果和灰度标签，形成结构化上下文。
3. LLM 根据上下文选择对应业务领域 Skill，并调用分析能力。
4. 结合事实和业务规则，组织证据与分析报告。
5. 通知下游，由使用者读取报告并采取措施。
6. 研发承接报告上下文，通过 Coding Agent 与 Ask-Venture 深入定位和修复。

用户强调程序预查询准备事实，不应改写成全部查询、计算均由 LLM 自由生成，或把所有事实采集都放在 Skill 选择之后。后续分析能力的具体工具清单未逐项展开，不自行补写。

## 主案例：实例充足，用户为什么仍在排队？

### 表象与调查成本

一次“用户分配排队”告警，监控显示可用实例充足，但调度无法分配。原先技术支持需要联系研发、测试，重新介绍上下文，再逐层查询日志。

### 业务解释与历史处置

这批实例所在业务要求预启动成功才能分配。虽然基础状态正常，预启动却失败，且集中在最近灰度的实例上。用户描述该次故障最终通过回滚恢复。

核心判断：监控上的“实例可用”，不等于满足业务规则的“可分配”。这一规则只用于描述该业务，不推广为所有云游戏实例都必须预启动。

### Agent 承担的第一轮调查

- 程序提供实例状态、预启动结果与灰度信息。
- Skill 提供该业务的分配前置规则。
- LLM 解释基础状态正常仍无法分配的原因，识别异常集中在灰度实例，为止损提供依据。
- 技术支持查看报告后识别受影响实例，通知运维停止灰度、回滚。
- 研发读取上下文，再通过 Ask-Venture 追查预启动失败的具体原因并完成后续修复。

### 叙事边界

原故障“回滚恢复”与当前 Agent 支持的典型流程分别记录，不擅自声称那次故障全程由 Agent 实际闭环处理。若需要将其展示为一次完整的 Agent 实战，再确认该次报告与后续处理的实际记录。

Agent 给出阻塞条件、影响范围和灰度关联；预启动为何失败仍需深入调查。停止灰度、回滚由人员决定并执行，不宣称系统自动回滚、自动修复或已独立证明灰度版本中的具体代码根因。

## 与 Ask-Venture 的分工

| 项目 | 在案例中的作用 |
| --- | --- |
| 启动性能分析 Agent | 从告警出发，识别影响范围、业务阻塞条件和灰度关联，为止损提供依据 |
| Ask-Venture | 承接调查上下文，深入日志、运行状态与代码，定位预启动失败的具体原因 |

这是人员衔接的工作流程，不补写两个系统之间自动调用或自动传递上下文的接口。

## 原网站保留的技术细节

- 固定 SQL 与固定 Python 脚本封装为参数化查询、聚合与变化量计算，数值来自确定性计算层；不让 LLM 自由生成报表数值。
- 内部监控、MySQL 与分析查询平台；可按版本、时段和机房等维度分析。
- 报告推送 Webhook，由下游邮件或企微通知。最新口述确认通知下游，但没有新增具体发送成功率。
- 固定计算不自动保证源数据、统计口径或归因正确，Webhook 接收不等于通知已送达。
