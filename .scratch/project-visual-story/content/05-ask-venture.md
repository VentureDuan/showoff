## 建议开篇

研发、测试和运营排查云游戏问题时，需要跨 Union 日志、实例日志、任务状态、数据库和代码逐层追踪。真正的瓶颈不仅是查询工具分散，还包括跨模块知识与人员协作。Ask-Venture 将领域知识、取证工具和调查流程组织到 Coding Agent 中，帮助使用者建立证据链、定位问题边界，并为后续研发处理提供上下文。

跨模块调查减少了多少人工协作尚无量化证据，不声称替代所有模块负责人。

## 从历史会话提取的典型使用流程

1. 用户描述环境、目标实例、故障现象；可附截图、父任务号或 flowId，不要求用户先知道根因。
2. Gateway 检查目标和信息是否足够，明确调查范围，选择部署/加速、游戏生命周期、实例状态等领域。
3. 需要实例取证时先检查远程通道 Gate；历史中有通道健康复检和按当时授权临时 bootstrap。不能将这些行为概括成完全零变更。
4. 加载相应领域 Skills 与参考知识，通过 MCP 工具和本地代码阅读收集证据。
5. 根据任务、尝试、会话标识及时间窗建立关联，找最后成功步骤与最早失败边界；分离原始故障、重试、取消和清理阶段。
6. 随证据调整路径，对照运行配置、二进制版本和代码；工具受限时明确缺口，不把查不到当成不存在。
7. 输出原因或已缩小的故障边界、证据、排除项、缺失证据和下一步。用户可继续追问版本、修复覆盖范围或其他现象。

现有网站还记载 handoff Skill 可导出 Markdown；这三段选定会话没有充分展示实际导出交接文件的完成证据，不能把“工具具备此能力”写成三次都完成交接。

## 建议主案例：表面取消报错，实际是磁盘容量不足

### 用户入口

给出环境、实例、父任务及失败截图，请求分析游戏加速失败。截图显示 task not found 一类取消阶段报错。

### 调查过程

- 选择部署/加速领域，检查远程通道并查找实例轮转日志。
- 远端长时间解压查询失败后，复检通道，改为下载必要的轮转日志到工作区本地筛选，未把通道错误当成无日志。
- 按原任务标识回溯，发现复制前的磁盘空间检查已失败。
- 对照代码中的新增包体、空闲容量和预留空间计算规则；同任务换用其他源后仍在同一空间检查处失败。
- 将之后的取消和 Finalizer 与原加速任务时间线分开。

### 历史结论与展示价值

原加速失败原因是目标 L2 盘装不下所需内容；task not found 是后续取消已失败任务时的次生报错。展示“按任务阶段和时间关联日志、再用代码解释判定”的能力。

历史诊断未执行扩容、清理或重新发起加速，不写成已修复并恢复业务。页面不需要公开精确容量或任务标识。

## 补充案例一：跨存储层与操作系统关联证据

- 用户反馈游戏加速失败。
- 历史调查显示 Ceph clone、rbd map、attach 已成功，Windows 添加游戏盘访问路径失败，返回 StorageWMI 42012。
- 同时间窗 partmgr Event 58 报告磁盘签名冲突，关联映射与盘符操作定位失败边界。
- 输出修复方向，未执行修改磁盘签名、盘符、上下线或重启。

可展示跨 Agent、存储与 Windows 系统事件的调查能力。历史会话将签名冲突判断为高度确定，磁盘与 image 的关联仍来自时间线，不冒充系统事件直接记录完整对象关系。

## 补充案例二：相似症状，区分本地与云端状态

- 同一主机两个实例均预启动失败，分别关联各自 Session 和任务证据。
- 一类是本地旧 Session 未结束，阻塞后续请求；另一类是 Agent 重启后本地 Session 丢失，但云端仍保持预启动态，取消后状态未收敛。
- 用户追问已包含取消修复为何仍失败，调查进一步比对运行二进制、提交作用范围和消费端代码。
- 历史结论区分接口幂等成功与业务状态真正收敛。消费端业务过滤是否是最终断点仍缺对应日志/配置证明，不把候选路径当成已完全证实根因。

可展示多实例隔离、运行证据与代码关联，以及修复覆盖范围判断。已部署修复也不自动意味着现场所有路径被覆盖。

## 未完全闭环的例子：串流失败与页面状态异常

同一会话还有后续串流调查：游戏进程已启动、session ID 已分配，但串流 Session 未 ready；本地采集与状态发送正常，云端持久化到页面链路缺少证据。查询工具的区域范围不匹配，不能用查询无结果证明消息丢失。

这段适合说明“输出证据边界和下一步”，不适合作为已定位全部根因或自动修复的成功案例。

## 领域 Skills 的组织与调查方法

以下为用户 2026-10-20 新增口述。

### 从真实故障提炼，按生命周期组织

- 从真实故障提炼调查方法，按部署加速、游戏启动与串流、实例状态上报等领域拆分。
- 每个领域明确入口条件、状态含义、关键标识和应查询的系统。
- 按需加载上下文，避免同时加载全部知识。
- 设计原则是启发模型调查，而非把模型限制在固定调用脚本中；不能要求每次工具调用顺序完全一致。

### 将排障习惯转为证据约束

1. 确认环境、实例、Agent 版本及时间范围；必要时将本地代码仓库切换到对应分支，对齐现场版本与代码。这里只记录历史方法，不授权当前会话切换其他仓库。
2. 按任务或会话标识关联证据，找到最后成功步骤与最早失败位置。
3. 区分原始故障与后续取消、重试、清理产生的报错。
4. 交付结论、支持证据、未确认项与下一步。
5. 证据不足时停在已确认的故障边界，不补出貌似完整的原因。
6. 根据真实使用中的误判补充反例与检查规则，减少同类问题重复出现。

### 用例结构

- 用户输入：当时提供的环境、实例、截图或错误描述。
- 测试环境：脱敏日志、数据库快照、对应版本代码及可调用工具。
- 预期判断：应定位的原因，或只能确认到的边界。
- 必须引用的证据与禁止结论：防止猜对原因却引用错误证据。

### 两层验证

| 层次 | 验证内容与边界 |
| --- | --- |
| 离线回放 | 固定材料或模拟 MCP 返回值，验证路由、查询参数、证据关联与判断，适合稳定回归 |
| 隔离环境集成测试 | 验证真实 MCP 连接、权限、分页、超时、查询范围；离线回放不证明这些能力 |

### 质量维度

| 维度 | 判断方式 |
| --- | --- |
| 目标与范围 | 是否查对环境、实例、时间窗及任务 |
| 诊断结果 | 是否定位正确原因，或正确停在证据边界 |
| 证据支持 | 结论是否有对应证据，是否混用其他任务日志 |
| 不确定性 | 缺日志或工具失败时，是否避免强行归因 |
| 操作边界 | 是否存在未经授权的写入、重启等行为 |
| 效率 | 成功用例的耗时、工具调用数与 token 成本 |

“证据不足但准确说明缺口”可以通过；“猜中根因但引用错证据”不能通过。越权单独作为硬失败，不能被其他得分抵消。

### 对照与迭代

- 固定模型、工具、材料与预算，对比基础 Agent + MCP，以及相同配置 + 领域 Skills。
- 每个案例重复运行，观察成功率与稳定性，不只展示最好一次。
- 失败按知识缺失、工具契约、取证策略或错误归因归类，针对性修改后回归。
- 不要求工具调用顺序完全一致，以调查质量与边界为准。
- 未提供实际对照数值，不声称成功率、稳定性或成本已提升特定比例。
