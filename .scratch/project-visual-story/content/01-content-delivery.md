# 云游戏内容分发与分层加速

状态：本轮口述已收敛，供后续网站编辑使用。

## 建议叙事

在实例带宽与业务成本受限的情况下，协调中心到边缘的大型游戏包交付，满足两小时版更开服窗口；通过部署与加速解耦、差量传输、P2P 与流水线优化关键路径，再利用观测数据优化双开机器的加速长尾。

## 业务背景与约束

- 分发对象为游戏包压缩包，方向为中心到边缘。后续优化的最终交付链路是打包分片、不压缩；不要因早期对象描述而误写为最终仍压缩。
- 游戏文件可超过 200 GB。
- 实例网卡受业务成本限制，通常为 1G 或 2G；以 1G 跑满带宽估算，全量传输至少约 30 分钟，大并发下可能更久。
- 客户订单约 1.5 万路，包含单开与双开机器，不等于 1.5 万台机器。
- 两小时是整个游戏版更到开服的总窗口，不是单独给下载或加速的时间。
- 业务要求至少 95% 成功率，剩余容量通过冗余机器解决。部分故障机器如无运维介入，可能始终不能下载成功。
- 速度、稳定性和可观测性都是关键要求，需要了解各阶段耗时、成功率和卡点。

## 个人贡献

全流程深度参与，重点负责部署和加速。不要写成四个领域全部独立实现。

## 四阶段模型

| 阶段 | 职责 |
| --- | --- |
| 装载 | 在装载机上按平台格式打包客户提供的游戏包，上传到自有 OSS |
| 分发 | 边缘机房分发机从 OSS 下载游戏包，解压并制作 Ceph 快照（这是最初介绍的流程；最终不压缩链路不要额外增加解压步骤） |
| 部署 | 实例通过 rbd-client 从 Ceph 快照克隆出克隆盘，并挂载到实例 |
| 加速 | 将游戏包或游戏文件拷贝、下载到更高速存储，改善体验 |

存储分层：L3 为 Ceph 网络盘，L2 为 SSD，L1 为内存盘。未确认所有任务都依次经过 L3 → L2 → L1，不将其画成强制顺序。

## 全流程优化

1. 装载：重点业务、重点客户使用独立高性能机器，结合 rclone 文件差量拷贝，控制在约 15–20 分钟。
2. 部署先行：Ceph 盘部署完成，实例即可外放，游戏从网络盘启动。加速拷贝后置，在保证客户可用实例数的前提下限速加速。
3. 下载更快：机房内部署 Dragonfly，实现 P2P 下载。
4. 下载更少：CDC 差量；一次代表性实际对比中，约 200 GB 游戏包，文件级差量约 170 GB，CDC 差量约 15 GB。不可推广为所有版本的固定收益。
5. 流水线：打包分片，使上传、下载等阶段重叠。早期讨论过压缩、上传、下载并行；最终方案明确不压缩。

## 设计取舍一：内容身份与业务版本分离

- 候选 A：游戏集 ID + 游戏集 version；每次游戏更新视为版本更新，不支持不同游戏集之间做 CDC 差量。
- 候选 B：内容分发领域不沿用游戏集版本建模，使用全局唯一 ID 标识文件包，支持任意文件包之间做 CDC 差量。
- 最终采用 B。这里描述的是内容分发领域的模型，不代表业务侧删除游戏集版本概念。

## 设计取舍二：打包与压缩分别验证

- 不打包时，文件数量和 peer 节点增加，观察到 Dragonfly 内存急剧增长，因此需要打包。用户曾用“指数级暴增”描述现象，缺少严格测量时不宣称指数复杂度。
- 压缩虽然节省下载量，但压缩、解压消耗时间，端到端测试没有总耗时收益。
- 最终链路：打包分片，不压缩。

## 实际结果与口径

以下均为用户根据回忆提供的多轮压测后的平均水平，已脱敏、取整，不是同一轮测试中的精确时间线。

| 指标 | 口述结果 |
| --- | --- |
| 部署完成、机器可用 | 约 70 分钟内超过 98% |
| 加速完成 | 约 140 分钟内 90% |
| 加速完成 | 约 160 分钟内 99% |
| 装载 | 多轮平均约 15 分钟 |
| 机房分发 | 多次 P98 耗时的平均值约 40 分钟 |
| 实例部署 | 多次 P98 耗时的平均值约 5 分钟 |

- P98 的多轮平均值不等于合并所有样本后的 P98，也不是普通平均耗时；不能将阶段数字直接相加推导总耗时。
- 开服窗口针对部署可用，加速可延后；不要声称所有机器两小时内完成。
- 加速受限速策略影响，其耗时不作为纯下载能力基准。

## 通过观测优化双开长尾

约 140 分钟时加速完成约 90%，剩余约 10% 主要是双开机器的第二路未完成拷贝。观察后调整算法，第二路从同实例第一路已有内容进行加速，将原约 210 分钟缩短到约 160 分钟，约缩短 24%。

旧方案 210 分钟的精确百分位口径未确认，不写成“P99 从 210 降至 160 分钟”。不推断同实例复用的具体拷贝机制。
